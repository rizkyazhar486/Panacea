# Strength log storage and calendar boundary

The original global `pmd_beban_v1` cache let a second account see a first account's saved exercise records. The actual previous built form reproduced two visible instances of account A's private movement on account B's page. New records use the existing account/self-subject storage adapter; unowned legacy bytes are retained without being adopted, overwritten or deleted.

The mounted page and derived Home widget agree with the remembered account, remount or clear on identity changes, and react to storage/focus/session expiry. Reads and synchronous writes/deletes check the mounted account binding; the adapter rechecks the current token before writing. Guests keep only component-local ephemeral records. Failed storage writes return the previous persisted list; the form reports failure and retains the draft, rather than inventing a successful save.

Date-only fitness records use local calendar days. The previous UTC comparison rejected a legitimate 13 October entry after midnight Jakarta while UTC was still 12 October; rolling-week bins also omitted that valid 500-kg-volume record. Validation and seven-day bins now use the same local calendar reference. Tomorrow is still rejected, including the paired Los Angeles case where UTC has advanced a day first. Stored owned history is validated for real calendar dates and original shape/ranges but is not discarded merely because the user travels to another timezone. Date-only records are not exact UTC event timestamps.

`strength-cache-scope.mts` checks two identities, stale reads/writes/deletes, legacy retention, expiry/future sessions, anonymous persistence refusal, quota failure, invalid IDs, Jakarta/Los Angeles calendar boundaries and history retention. `strength-cache-smoke.mjs` exercises actual synthetic mobile page/Home widget behavior in Asia/Jakarta: an A-positive widget hides after another tab changes identity, B cannot read A's saved sessions, A restores its data, unassigned legacy records stay hidden and unchanged, and quota failure leaves the draft intact. Existing draft and stored-set-integrity assertions remain active; their fixture keys now target the attributable test account.

This is a client cache and engineering behavior check. It is not encryption, an XSS/device-administrator defense, server RBAC, clinical approval, biomechanical validation, or privacy closure for every other cache. Repetitions/load limits, volume/Epley formulas and clinical cautions are retained; clinically_reviewed=false.
