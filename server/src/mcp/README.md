# Panaceamed MCP kernel

This directory is the project-owned orchestration boundary between Panaceamed capabilities and MCP clients. Phase A now includes the policy/audit kernel, ChatGPT/Claude Code coordination packets, local repository-QA allowlist, official MCP SDK v2 transport wiring, and production-safe Express mounting.

## Safety boundary

- **Remote MCP is disabled by default.** `/api/mcp` remains mounted behind the API limiter but returns a deterministic 404 unless `PANACEA_MCP_HTTP_ENABLED=true`.
- **No patient-record retrieval.** Remote-safe tools may process caller-supplied preview data in later phases, but this MCP kernel does not fetch arbitrary patient records from the Panaceamed datastore.
- **No arbitrary shell.** Repository QA accepts only named profiles that resolve to fixed `npm` executable/argument arrays with `shell: false`.
- **No direct push to main.** GitHub remains the authoritative branch/PR/CI/merge source, and repository policy still requires short-lived branches, PRs, exact-head gates, and the final latest-main audit.
- No SATUSEHAT submission, autonomous EMR signing, medication commit, order commit, diagnosis, or treatment is exposed by this kernel.
- Audit records summarize request shape and byte size only; raw clinical values and credentials are not retained by the audit helper.

## Phase A tool surface

| Tool | stdio | HTTP policy | Side effect |
| --- | --- | --- | --- |
| `panacea_capabilities` | allowed | allowed | none |
| `panacea_orchestration_create_task` | allowed | allowed | none |
| `panacea_orchestration_create_handoff` | allowed | allowed | none |
| `panacea_orchestration_verify_completion` | allowed | allowed | none |
| `panacea_repo_qa_plan` | allowed | denied | local-read |
| `panacea_repo_qa_run` | allowed | denied | local-test |

HTTP capability discovery filters the registry through the same authorization policy used by execution. A local-only tool therefore cannot become remotely callable merely because it exists in the registry.

## Local stdio host

The stdio transport is the preferred path for Claude Code or another authorized local MCP host because repository QA remains local-only.

From `server/`:

```bash
npm run mcp:stdio
```

The stdio host supplies the repository root as trusted host context. MCP callers can choose a named QA profile but cannot choose an arbitrary executable, argument vector, shell command, or repository path.

## Remote Streamable HTTP

The production backend mounts MCP at:

```text
/api/mcp
```

Remote access is off unless both conditions are satisfied:

```bash
PANACEA_MCP_HTTP_ENABLED=true
PANACEA_MCP_HTTP_BEARER_TOKEN=<random secret with at least 32 characters>
```

Do not commit or log the bearer token. Requests without the correct `Authorization: Bearer ...` header are rejected before they reach the MCP transport. HTTP runs statelessly with the official `NodeStreamableHTTPServerTransport` and exposes only tools whose registry policy explicitly allows the `http` transport. Repository QA is not remotely exposed.

## Official SDK dependencies

Phase A uses the stable MCP TypeScript SDK v2 package split:

- `@modelcontextprotocol/server@2.0.0`
- `@modelcontextprotocol/node@2.0.0`
- `@modelcontextprotocol/express@2.0.0`
- `zod@4`

Dependency metadata and `server/package-lock.json` were generated by npm. **Do not hand-edit `server/package-lock.json`.** The application remains on Express 4; the stable MCP Express package supports the existing Express major, so no framework-major migration was required.

## Repository QA profiles

The caller supplies only one profile name:

- `server_typecheck`
- `mcp_targeted_tests`
- `root_validators`
- `root_build`
- `server_full_tests`

Each profile expands to fixed executable/argument arrays. The child-process environment is rebuilt from a small operational allowlist instead of inheriting application credentials.

## Orchestration semantics

Task packets record the base-main SHA, branch, scoped paths, acceptance criteria, and required checks. Handoff packets record what actually changed, checks actually observed, unresolved risks, and the next permitted action. Completion verification keeps these states separate:

`implemented -> tested -> PR-open -> merged -> deployed`

Later states require their own evidence. For example, `implemented: true` never implies `tested: true`, and a merge/deployment claim is rejected when its evidence field is absent.

## Verification

From `server/`:

```bash
npm ci
npm run uji:mcp
npm run typecheck
```

The MCP test suite covers policy/audit redaction, orchestration evidence state, QA allowlisting and environment stripping, registry dispatch, stdio/HTTP construction, HTTP default-off + bearer authentication, remote QA exclusion, MCP initialize, and production backend mounting behind the global API limiter.

## Specialist connector boundary

The MCP kernel complements specialist connectors rather than replacing them. GitHub remains authoritative for remote repository state and CI evidence; Context7 supplies current SDK documentation; literature connectors remain evidence-retrieval specialists; deployment/analytics/email/growth connectors retain their own operational responsibilities. ChatGPT can orchestrate those tools and normalize their outputs into later Panaceamed MCP phases without presenting the LLM itself as a clinical or academic source.
